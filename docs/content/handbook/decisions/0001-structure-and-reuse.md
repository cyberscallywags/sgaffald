# Application structure, storage and reuse review

Status: **accepted**, partly carried out. Recorded 23 October 2026, before the package was
renamed to `app` and the brand moved to `brand/`; paths below are as they were then.

Reviewed: 23 October 2026. Scope: the local Sgaffald application, Docker builds, documentation, dependency manifests and CI workflows.

## Recommendation

Keep the existing service boundaries and Python package stable. Build on the validated `src/sgaffald/content/site.json` manifest to introduce a small, versioned project metadata contract. Use it to supply branding and project information to the application and documentation, with generated adapters for mobile build configuration. Rebranding should not require renaming Python imports, Docker services or API routes.

The largest storage opportunities are dependency installation and generated output, rather than application source. Separate developer tool groups, improve ignore rules, and narrow Docker copy operations before considering a major directory restructure.

This report proposes changes only. No application configuration, dependencies, generated output or database data was changed or deleted.

## Evidence and limits

Measurements use local `du -k` allocated storage, converted to MiB (1,024 KiB). They describe this working directory, not compressed download sizes, Docker image sizes or Git history. No `.git` directory is available here, so tracked-file status and repository history could not be checked. Files excluded by `.gitignore` can still exist locally; ignore rules do not reclaim storage.

| Location | Approximate size | Interpretation |
|---|---:|---|
| Entire working directory | 1,182 MiB | Dominated by installed dependencies |
| `.venv/` | 754 MiB | Reconstructible Python environment |
| `src/sgaffald/mobile/node_modules/` | 408 MiB | Reconstructible JavaScript dependencies |
| `src/sgaffald/mobile/.angular/` | 11.4 MiB | Angular cache |
| `src/sgaffald/mobile/www/` | 0.96 MiB | Compiled mobile web output |
| `docs/_build/` | 4.71 MiB | Generated portal and manual |
| `docs/.cache/` | 1.07 MiB | Documentation cache |
| `docs/content/assets/images/` | 0.50 MiB | Small; not a priority |

The two installed dependency trees account for approximately 98% of measured storage. Removing both would reclaim approximately 1,162 MiB locally, but subsequent development would require reinstalling them. Cache and build directories above offer approximately 18 MiB of additional reclaimable space. These are alternative cleanup targets, not a promise of permanent savings for an active development environment.

Docker daemon storage, BuildKit caches, external package caches, browser downloads and Neo4j volume contents were not measured.

## Existing structure: preserve the useful parts

- `src/sgaffald/api`, `ui` and `admin` provide understandable service boundaries.
- Shared models, settings, database access and content loading already avoid several duplicated implementations.
- `tests/unit`, `integration`, `e2e` and `load` communicate test scope clearly.
- Docker already uses multistage builds, service-specific Python extras and static nginx runtime images for mobile and docs.
- Python packaging excludes the mobile directory from the wheel. Keep this safeguard.
- Both documentation engines share `docs/content`; reference pages are generated by `sgaffald.docgen`.
- Lockfiles and existing strict documentation builds are valuable for reproducibility. Keep them.

## Prioritised storage and build optimisations

| Priority | Finding and evidence | Recommended change | Expected benefit |
|---|---|---|---|
| High | `.gitignore` omits mobile `node_modules`, `.angular` and `www`; `.dockerignore` already excludes them | Add explicit rules for those three directories. Check tracking in a real Git checkout before removing any indexed artifacts | Prevent accidental inclusion of roughly 420 MiB of local dependencies/cache/output in future commits or template copies |
| High | Default `dev` dependencies include all service extras and the entire `docs` group | Introduce focused groups for lint, unit tests, browser tests, load tests and docs; retain an explicit full-development group | Smaller environments for contributors and CI jobs that use only part of the stack |
| High | All CI jobs run `uv sync --locked`, including mobile and docs | Install only the groups needed by each job. Mobile Docker tests need a lightweight host task runner, not the complete Python test/docs environment | Reduce repeated installations across jobs |
| Medium | `docker/Dockerfile` and `docker/docs.Dockerfile` copy all `src`, including mobile source | Copy only the Python package with mobile excluded, using a supported exclusion mechanism or curated build input. Docs should retain whatever source its references actually need | Less context consumption and fewer Python/docs rebuilds after mobile-only changes |
| Medium | The API, UI and admin depend on shared base dependencies including Neo4j and HTTPX | Audit actual imports, then consider moving genuinely service-specific dependencies into extras | Smaller service environments; verify shared imports before changing dependencies |
| Medium | Portal and manual render much of the same material twice | Keep both if they serve distinct audiences. If one is redundant, select a primary renderer before removing the other | Lower tooling and maintenance cost; current generated site is only 4.71 MiB |
| Low | PNG and WebP crest variants coexist | Check references in both themes before pruning unused variants; retain needed favicon/logo sizes | Small saving; avoid spending disproportionate effort here |

Examples of Python environment contributors include Playwright (~138 MiB), PyArrow (~123 MiB), Zensical (~84 MiB), Pandas (~49 MiB) and Streamlit (~30 MiB). These sizes do not prove that a dependency is unnecessary: browser tests, admin functionality and documentation account for much of the footprint. Determine savings by measuring clean, task-specific installations after splitting groups.

Suggested additions to `.gitignore`:

```text
# Local mobile dependencies, cache and generated web bundle
src/sgaffald/mobile/node_modules/
src/sgaffald/mobile/.angular/
src/sgaffald/mobile/www/
```

Provide separate, documented cleanup tasks for generated outputs and installed environments. Preview exact paths before deletion; do not combine them with database cleanup. `task down` currently runs `docker compose down -v`, which removes the Compose volumes, including `neo4j-data`. Keep that behaviour explicitly labelled as a disposable test-stack operation and avoid using it as general storage maintenance.

## Project metadata: extend the existing mechanism

### What already works

`content/site.json` contains brand, theme, welcome/about content and sidebar pages. `content/__init__.py` validates it with Pydantic and supports an alternate file through `Settings.site_file` / `SITE_FILE`. `GET /site` supplies the result to the web and mobile frontends. Existing tests cover custom files, invalid colours, duplicate slugs and reserved routes.

This is already a useful foundation for reusable applications. The gap is project-wide adoption:

| Repeated information | Current locations | Proposed authority |
|---|---|---|
| Name, tagline, collective, theme | `content/site.json`, mobile fallback and SCSS defaults | Project manifest |
| Docs name, author and description | `docs/sphinx/conf.py`, `docs/zensical.toml` | Project manifest through build adapters |
| API title and description | `api/main.py`; UI title also set in `ui/main.py` | Project manifest |
| Release version | `pyproject.toml`, API, Sphinx; mobile currently uses a different version | Python package metadata for shared release identity; document mobile version policy |
| Native name and identifier | `mobile/capacitor.config.ts` | Manifest build settings; applied before native packaging |
| Repository and support links | README placeholders and docs configuration | Project manifest; generate bounded README sections |
| Service names, routes and entrypoints | Compose, nginx, Docker entrypoint and application modules | Keep explicit structural configuration |

### Proposed contract

Add `src/sgaffald/content/project.json` as the bundled project identity file. Keep page content in the existing `site.json`, but migrate `brand` and `theme` ownership to the new manifest. A loader should compose both files into the existing `Site` response so consumers need not change their public contract immediately.

For backwards compatibility, continue accepting legacy complete `SITE_FILE` documents during migration. Define precedence explicitly: a selected legacy site file supplies its brand/theme; otherwise use the selected project file plus the bundled or selected page content. Reject ambiguous combinations after a documented transition rather than silently merging contradictory values.

Proposed project file (illustrative; not currently supported):

```json
{
  "schema_version": 1,
  "project": {
    "slug": "sgaffald",
    "name": "Sgaffald",
    "description": "A reusable application foundation.",
    "tagline": "Build, learn, share and grow.",
    "collective": "Cyber Scallywags"
  },
  "links": {
    "collective": "https://cyberscallywags.com",
    "repository": null,
    "support": null
  },
  "theme": {
    "primary": "#1b4965",
    "secondary": "#5fa8d3",
    "tertiary": "#e4572e"
  },
  "mobile": {
    "app_id": "com.cyberscallywags.sgaffald",
    "app_name": "Sgaffald"
  }
}
```

JSON fits the current application, works naturally across Python and TypeScript and avoids another parser dependency. Keep explanatory guidance in the generated schema and docs, since JSON does not support comments.

### Ownership and validation

- Add Pydantic `ProjectMetadata` models with `extra="forbid"`, a supported schema version, nonempty names, validated slugs, colour formats and appropriate URL validation.
- Generate a JSON Schema for editor completion and early feedback. Validate selected project and page files before starting the application or building docs/mobile.
- Add a proposed `PROJECT_FILE` setting. Bundle the default using package resources and prove it is present in a built wheel; avoid relying on the current working directory.
- Keep `pyproject.toml` authoritative for Python distribution name and version. Read installed version with `importlib.metadata`; use a deliberate build-time source-tree fallback for docs. Avoid a second editable release version in JSON.
- Decide explicitly whether mobile follows the application release version or has an independent release cycle. Native platform build numbers remain separate.
- Keep secrets, database credentials, model provider keys and deployment URLs in environment settings. `DOCS_URL` already follows this pattern. Publish only an allowlisted public metadata view.
- Treat `mobile.app_id` as build identity: changing it after app-store publication may represent a different application. A routine brand edit must not rewrite it automatically.
- Manifest content must remain data: no Python import paths, shell commands or arbitrary executable templates.

### Loading and update behaviour

The current `get_site()` uses `lru_cache`, so editing its file does **not** hot-reload running API workers. Document restart/reload requirements. Do not promise immediate propagation merely because frontends read `/site`.

Compose currently neither forwards `SITE_FILE` nor mounts a custom manifest. Add an explicit deployment override with a read-only manifest mount and the corresponding container path setting; setting a host variable alone will not make a host file accessible inside the container. Apply the same approach to the proposed project file.

Docs, mobile fallback colours, browser shell metadata and native configuration are build outputs. Generate them before their respective builds. A docs build receives metadata through a generated temporary configuration overlay; Sphinx can read validated metadata directly. Avoid hand-editing entire tool configuration files or replacing arbitrary text.

Generate the mobile fallback and theme defaults from the manifest to prevent first-launch branding drift. Namespace its existing `sgaffald.site` and `sgaffald.member` storage keys using a stable project identity and schema version; consider API origin when one browser can access multiple backends. Validate cached content rather than relying only on a TypeScript cast, and define expiry/migration rules.

## Reuse and directory layout

For the first iteration, keep current directories and add the metadata loader plus a small build-generation module. Moving files alone saves no storage and causes unnecessary churn.

If the frontend grows independently, a later layout could be:

```text
src/sgaffald/           # Stable Python package: API, UI, admin, shared models
  content/
    project.json       # Default project identity
    site.json          # Page content after migration
apps/mobile/           # Ionic project, moved in a separate change
scripts/               # Thin metadata/schema/build adapters
schemas/               # Generated public JSON Schema
services/              # Optional deployment overlays, only if needed
docker/                # Image definitions and nginx templates
docs/content/          # Authored documentation
reports/               # Review artifacts
tests/                 # Unit, integration, browser and load tests
```

A mobile move requires updates to Docker COPY paths, `.dockerignore`, `.gitignore`, documentation, tests and any packaging exclusions. Keep it separate from the metadata migration.

Stop recommending global search-and-replace for routine branding in `docs/content/guides/make-it-yours.md`. Preserve `sgaffald` as an internal package identity unless a real distribution rename is required. Docker service names such as `api` and `neo4j`, internal hostnames, reserved routes and domain models should remain structural. Adding new domain behaviour still requires code changes.

Generate TypeScript API types from OpenAPI or a shared schema to reduce manual duplication in `mobile/src/app/core/api.service.ts`. This primarily improves reuse and correctness, not disk size. Keep renderer-specific code explicit rather than attempting to generate entire frontends from metadata.

## Suggested implementation sequence and acceptance checks

1. Add the missing mobile ignore rules and a documented, scoped cleanup task. In a real checkout, verify generated directories are untracked. Retain both lockfiles and all required assets.
2. Split dependency groups and update CI installation commands. Measure clean environments and Docker images before/after; keep unit, integration, mobile, browser and strict docs gates passing.
3. Add validated project metadata, schema generation and the compatibility loader. Test unknown keys, unsupported versions, invalid values, missing files and legacy `SITE_FILE` behaviour.
4. Wire API/docs branding and generated mobile defaults to the same source. Change a fixture project name and colours and confirm all surfaces agree while routes, imports, Compose names and database settings remain unchanged.
5. Add read-only deployment overrides and document restart versus rebuild requirements. Verify an installed wheel, a container deployment and offline mobile startup use the expected identity.
6. Add a CI generation check to detect stale generated files. Test generation twice for idempotence and verify package release versions agree with the intended tag policy.
7. Consider frontend relocation and retiring a documentation renderer only after the higher-value changes are measured.

The recommended first deliverable is a compatible metadata layer and generated branding adapters, followed by focused dependency installs. This provides easier reuse without requiring an application-wide rename or architectural rewrite.
